### [MEDIUM] PageDown and loadFiles clamp cursor against len(m.files) instead of the displayed (filtered/tree) list

**Location:** `update_keyboard.go:1997`

Up/Down and mouse wheel correctly bound the cursor with m.getMaxCursor() (update_keyboard.go:1673/1696, update_mouse.go:1145), which uses getFilteredFiles()/treeItems. PageDown instead clamps with `if m.cursor >= len(m.files) { m.cursor = len(m.files)-1 }` in both dual-pane (lines 1969-1974) and single-pane (lines 1996-2002). The displayed list length routinely differs from len(m.files): tree mode with expanded dirs is longer (treeItems), changes mode shows m.changedFiles, git-repos mode shows gitReposList, prompts mode adds virtual entries, and an active search filter is shorter. Result: PageDown either can't reach the end of the list (tree/changes mode) or overshoots past the filtered list so getCurrentFile() returns nil and the cursor highlight disappears (search mode). Related: loadFiles' clamp `if m.cursor >= len(m.files) { m.cursor = 0 }` (file_operations.go:490) resets a perfectly valid cursor to 0 in changes mode whenever a watcher fileChangedMsg fires, because the cursor indexes changedFiles (often longer than the cwd listing) — the selection jumps to the top mid-review.

**Fix:** In both PageDown branches (update_keyboard.go ~1969-1974 and ~1996-2002), replace the len(m.files) clamp with: maxCursor := m.getMaxCursor(); if m.cursor > maxCursor { m.cursor = maxCursor }; if m.cursor < 0 { m.cursor = 0 } — matching the existing down-arrow/wheel logic. In loadFiles (file_operations.go:490), clamp against the displayed list instead: if max := m.getMaxCursor(); m.cursor > max { m.cursor = max }; if m.cursor < 0 { m.cursor = 0 } — preserving position instead of jumping to top. Additionally, since update.go:475 replaces m.changedFiles *after* loadFiles() returns, add the same clamp right after `m.changedFiles = changed` in the fileChangedMsg handler so a shrunken changes list cannot leave the cursor out of bounds.

### [HIGH] Copying a file onto itself truncates the source to zero bytes (data loss)

**Location:** `file_operations.go:1426`

copyFileContent() opens src, then calls os.Create(dst) which truncates dst. m.copyFile() (line 1412) performs no validation that src != dst or that dst is not inside src. The copy-mode flow in update_keyboard.go:248-273 builds destPath = filepath.Join(destDir, sourceName); if the user picks the source's own directory as destination, destPath == sourcePath, so os.Create truncates the file while it is open for reading and io.Copy copies 0 bytes — the file content is permanently destroyed. Similarly, copying a directory into itself or a subdirectory of itself causes copyDirectory() (line 1449) to MkdirAll the destination inside the source before ReadDir(src), so the new dst appears in the entries and is recursively copied into itself until path-length failure, filling disk. There is also no exists-check, so any name collision at the destination is silently overwritten.

**Fix:** In m.copyFile() (file_operations.go:1412), before dispatching: resolve src with filepath.Abs+filepath.EvalSymlinks, and resolve dst by EvalSymlinks-ing its PARENT directory (dst itself usually doesn't exist yet, so EvalSymlinks(dst) would fail) then re-joining the base name. Reject with a clear error when (1) resolved src == resolved dst (for an existing dst, prefer os.SameFile(srcInfo, dstInfo) to also catch hardlinks), and (2) for directories, when dst is under src: strings.HasPrefix(dst, src+string(filepath.Separator)). Additionally os.Stat the destination and refuse (or route through the existing dialog system in dialog.go to confirm) before overwriting an existing file. Add unit tests in file_operations_test.go for: file self-copy leaves content intact, dir-into-itself rejected, dir-onto-parent (dst==src) rejected, and existing-dst collision behavior.

<details><summary>Verifier evidence</summary>

Verified in code: copyFileContent (file_operations.go:1426) does os.Open(src) then os.Create(dst), which O_TRUNC-truncates the same inode when destPath==sourcePath, and the copy flow in update_keyboard.go:237-285 builds destPath=filepath.Join(destDir, filepath.Base(source)) with zero src/dst validation — pressing Enter on the source file itself in copy mode reproduces the zero-byte data loss. The directory self-copy recursion and silent-overwrite claims also hold (copyDirectory at 1449 MkdirAll's dst before ReadDir(src)).

### [HIGH] moveToTrash rollback silently fails for cross-device trashing, losing track of the file

**Location:** `trash.go:168`

When metadata load/save fails after the file was moved to trash, moveToTrash attempts rollback with `os.Rename(trashedPath, path)` at lines 168 and 186, ignoring the returned error. If the original move required the copy+delete fallback (cross-device, lines 142-157), the rollback rename will also fail with EXDEV — silently. The function then returns 'failed to save trash metadata', the original file is gone from its location, and the copy sits in ~/.config/tfe/trash with NO metadata entry, so it is invisible in the trash view (convertTrashItemsToFileItems only lists metadata entries). From the user's perspective the file has vanished. The same orphaning happens on the same-device path if the rollback rename fails for any other reason (e.g. parent dir removed).

**Fix:** In moveToTrash (trash.go ~168 and ~186), capture the rollback os.Rename error. On failure (including EXDEV), attempt copyRecursive(trashedPath, path) followed by os.RemoveAll(trashedPath); if that also fails, return an error that includes trashedPath (e.g. "failed to save trash metadata; file preserved at %s") so the user can recover manually. Alternatively, append and save the metadata entry BEFORE moving the file and remove the entry if the move fails — this is safe because convertTrashItemsToFileItems already skips entries whose TrashedPath does not stat, so a transiently stale entry is invisible, and it eliminates the window where a trashed file is untracked. Severity is best classed medium-high: the trigger (metadata load/save failure) is rare, but the consequence is silent apparent file loss in a feature whose purpose is data safety.

Verified: trash.go:168 and :186 ignore os.Rename rollback errors; the cross-device forward path (trash.go:142-157) proves the reverse rename would also fail with EXDEV, and the trash view (file_operations.go:285-298 via convertTrashItemsToFileItems, trash.go:394-420) lists only metadata entries, so the orphaned copy is invisible to the user.
